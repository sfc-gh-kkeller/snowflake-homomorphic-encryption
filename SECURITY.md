# Security

## Scope of this project

This is a **demonstration** of homomorphic encryption (HE) on Snowflake. It is not an official Snowflake
product or feature, it has not been security-reviewed for production use, and it should not be used to
protect production data as-is.

## What the demo does and does not protect

* **Confidentiality from the platform:** sensitive values are encrypted on the client. Snowflake stores and
  computes on ciphertexts using only public parameters: the public encryption context and, in packed mode,
  public rotation keys. Secret keys never leave `keys/` on the client.
* **No integrity:** HE does not prove that a computation was performed correctly or on the intended rows. A
  malicious or buggy server could return a wrong (but well-formed) ciphertext.
* **Metadata is visible:** plaintext columns, row counts, query shapes, ciphertext sizes and the operations
  applied (see `HE_INFO`) are visible to the server.
* **Parameters:** BFV n=4096 (~128-bit security with q=[36,36,37]) and CKKS n=8192 (q=[60,35,35,60], 190 bits
  total, within the 128-bit HE-standard bound of 218 bits for n=8192). Secret keys are generated by Microsoft
  SEAL via Pyfhel.
* **CKKS is approximate**, and CKKS decryption results can leak information about the secret key if shared
  with untrusted parties (Li–Micciancio, 2021). Do not publish raw CKKS decryptions in an adversarial setting.

## Handling key material

* `keys/` and `config.toml` are gitignored. Run `scripts/scan_secrets.sh` before pushing.
* Losing `keys/` makes the encrypted data in Snowflake unrecoverable. Rotating keys means re-encrypting.

## Reporting

Please report security issues privately via GitHub's "Report a vulnerability" (Security tab) rather than in a
public issue.
